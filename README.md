# gff3-validator

A one-stop validator for [GFF3](https://github.com/The-Sequence-Ontology/Specifications/blob/master/gff3.md)
annotation files, built by FAIR-bioHeaders with the Sequence Ontology (SO) group.

> **Status: pre-release (0.0.1.dev0).** The rule catalogue is a draft under
> review with the Sequence Ontology group
> ([FHR-Specification #62](https://github.com/FAIR-bioHeaders/FHR-Specification/issues/62)).
> Only a small first slice of rules is implemented. Nothing has been published
> to PyPI or Bioconda. Do not rely on rule ids, levels or output formats yet.

## Goal

One place, one name, three interfaces (web page, CLI, library) that tell you
whether a GFF3 file is valid against the GFF3 specification (version 1.26) and
the Sequence Ontology, and that explain every problem in plain language with
the rule id, the line and a suggested fix. When a file carries a FAIR-bioHeaders
(FHGFF3) provenance header, the validator also checks it and its link to the
genome. See [spec 009](https://github.com/FAIR-bioHeaders/FHR-Specification/blob/main/specs/009-gff3-validator/spec.md)
(copied in [specs/001-gff3-validator](specs/001-gff3-validator/spec.md)).

Plain GFF3 without a header is a first-class input: core validation does not
depend on FAIR-bioHeaders.

## Rule catalogue

Every check is a numbered rule in [rules/catalogue.yaml](rules/catalogue.yaml),
rendered as [docs/rules.md](docs/rules.md). Each rule has an id, level
(error, warning, info), layer (core, FHGFF3, biology), a reference into
GFF3 1.26 or SO, a bad example and a fix, its implementation status and its SO
review state. Open questions for SO are collected in
[docs/questions-for-SO.md](docs/questions-for-SO.md). A suggested fix is
guidance only; the validator never rewrites a file.

[docs/EVALUATION.md](docs/EVALUATION.md) reviews the 2024 FHGFF3 prototype, the
LinkML GFF3 model and existing validators (GenomeTools, AGAT, GFF3toolkit, the
SO-era Perl validator, NCBI table2asn), with a side-by-side run on small broken
files.

## Planned interfaces

- **CLI** `gff3-validate FILE [--genome genome.fa] [--format text|json]`, reading
  plain, gzip/BGZF or stdin (`-`) input. Exit codes: 0 no errors, 1 errors
  found, 2 usage error or unreadable input (the run is then incomplete).
- **Library** `gff3_validator.validate(path)` returning findings with rule id,
  level, line, column, message and fix.
- **Web page** on the FAIR-bioHeaders site running the same engine in the
  browser through Pyodide, so files never leave the computer.
- **Reports** in text and JSON now; HTML and optional SARIF later.
- **Repository profiles** (NCBI, Ensembl, Alliance) layered on the core rules,
  later and only with each repository's review.
- **Distribution** on PyPI and Bioconda, a Galaxy wrapper, an FHR-Nextflow
  module and a container, after the first reviewed release.

Headers: a FAIR-bioHeaders header is validated when present; `--require-header`
makes it mandatory and `--no-header` skips header checks. Header checks need the
optional extra, `pip install "gff3-validator[headers]"` (FAIR-bioHeaders
toolkit 0.4). FHGFF3 support in the toolkit is not released yet, so the
skeleton only detects `#~` header lines and reports that header validation is
not implemented.

## Current skeleton

```bash
poetry install
poetry run gff3-validate tests/fixtures/valid/canonical_gene.gff3
poetry run gff3-validate --format json annotation.gff3.gz
```

The reader streams line by line. The implemented rules are per-line and keep no
per-feature state; structure rules (IDs, Parent resolution, cycles) will need
state, and their memory strategy is to be specified with
[#64](https://github.com/FAIR-bioHeaders/FHR-Specification/issues/64).
